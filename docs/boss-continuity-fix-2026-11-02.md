# Boss 面板连续显示修复

用户在 `411bc63` 游戏实测中仍看到 Boss 面板闪过、露出 Minimap。该反馈否定了上一轮「保留上层绘制槽即可解决现场闪烁」的完整结论。旧修复解决了下层占用最后可用槽的问题，但原验证主要检查恢复后的画面，没有要求被跳过的每一呈现帧仍有面板。本轮按完整丢帧链修复并补逐帧验证。新包尚未经过用户游戏复测，闪烁仍待现场验收；菜单预加载也尚未收到现场验收结果。

## 确认的丢帧路径

| 路径 | `411bc63` 行为 | 本轮处理 |
|---|---|---|
| 更新线程发布快照时，Boss 的快照锁暂忙 | 把锁竞争当成没有快照，返回成功但不提交网格 | UI 保留最后有效的 `Arc<Snapshot>`，取得新快照后才替换；无首次快照时返回暂忙 |
| 显示状态读取失败或 `valid=0` | 按不可见处理，整窗消失 | 区分可见、隐藏、未知；未知延续最后确认的显示决定，并释放输入、取消交互 |
| 新字符改变字体图集 | 网格立即使用新句柄，核心尚未把纹理移入 GPU 表；背景也依赖同一图集的白像素 | 新绘制包所需纹理全部可用后才发布完整成图；等待时合成上次完整成图，不以旧图集配新 UV |
| 图集创建请求暂未接收 | 仍提交新 UV 与旧 handle，或首次无 handle 时成功但空绘制；核心纹理注册表锁竞争就可触发返回 0 | 共享 UI 在提交前检查本次实际依赖的 managed texture，未成功更新则返回 `ERR_BUSY`，后续即使没有新 delta 也重试；不因无关的 dirty texture 阻塞 |
| 同一原生队列序号再次呈现 | 插件去重后没有网格，刚清空的目标没有 Boss | 保留核心拥有的完整 CPU 绘制包和 GPU 成图；重复序号只重放成图，不再次推进 egui 或消费输入 |
| 核心 GPU 锁、回调 gate 或插件 UI 锁暂忙 | 上层回调直接退出；Minimap 的下层内容可能仍在 | 将 UI 准备与 GPU 状态锁分开；暂忙使用独立的有界合成提交环 |
| 四个几何提交槽全部在途 | 即使给上层保留一个槽，也没有可重用 allocator | 使用独立的合成专用 allocator/list，不重置尚未完成的几何槽，也不等待 GPU |

`BossState` 暂时不可用本身只使进度未知或显示等待状态，不是整窗消失的已确认原因。原生桥的 L／游戏 UI／H 顺序与 C++ 一致；本轮未证实存在游戏原生命令反序，不把全部闪烁归因于层排序。

C++ 对照固定为 `afab7e14db2b62ae0bede980d5d0c96634321350`。`src/boss/data.cpp::fillRenderState` 在锁内复制发布状态；Rust 沿用旧快照以保留非阻塞约束，而不复制阻塞锁。`src/d3drenderer.cpp` 使用 `2 * swapchain.BufferCount` 个共享槽，忙时也会退出；其 `DrawLayers` 只在同一序号内共享 ImGui 数据，不提供本轮的跨帧 GPU 成图。C++ 字体上传等待完成；本轮不引入该等待。

## 成图、失效和资源所有权

每个上层插件保留一份核心复制的 CPU 绘制包，只有成功完成的回调才替换整包。`ERR_BUSY` 和重复回调保留旧包，非法输出或回调错误使对应包和成图失效。成功但没有绘制内容表示明确隐藏，不能当作暂忙继续重放。插件内存、egui 对象和借用网格指针不跨回调保存。下层仍跳过暂忙及重复序号，不重放旧地图几何，也不在同一序号再次应用 Minimap 透过率合成。

正常上层绘制完成后，将自身 RGBA8 离屏图复制到拥有的成图；保留组透明度、圆角、裁剪和边框参数，重放时应用一次。Minimap 的下层透过率合成保持不变。目标 RTV 每次从当前 UI_SCENE 回调借用，不保留游戏目标或依赖前帧目标像素。成图只在相同 device、queue、viewport 下复用；不兼容的设备或队列直接失效，不能向新队列提交旧资源。

当本层插件全都暂忙或只有重复包时，核心仍用空绘制推进既有的有界纹理上传，然后重放成图。否则，图集因 CPU 源队列额度不足被拒绝、所有 UI 又因此返回暂忙时，未上传的旧任务可能一直占着图集需要的额度。该维护不生成 UI 网格、不清掉成图、不增加上传额度，同一原生序号仍共享原有预算。

确认 loading／Logo 或全屏地图隐藏时，核心立即记录隐藏决定、释放输入并使成图失效。失效请求在暂时取不到成图锁时仍保留，下一次取得锁先执行失效；未知状态不能推翻已确认隐藏。只有重新确认可见才解除隐藏。手动关闭优先于 UI 锁竞争，重新打开前也保留隐藏通知。未知显示状态允许延续最后有效画面，但不消费输入、不保留鼠标／键盘捕获、不允许复活确认；复活仍重新核对存档上下文和旗标。

四个几何提交槽保持不变；另有固定 16 个仅用于合成的 allocator/list。每个列表只在自己的 fence 完成后重置，没有逐帧 GPU 等待或自动无限扩容。D3D12 不允许在上次执行尚未完成时重新执行同一 DIRECT command list，见 [ExecuteCommandLists 契约](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12commandqueue-executecommandlists)。成图最多 64 组、128 个描述符、128 MiB；替换后的图片与描述符同时等待几何复制 fence 和合成 fence。停止先禁止新提交，取得独立成图锁后再次核对停止状态；排空涵盖两组 fence。

四个几何槽不等于可容纳四个双层帧：Minimap 和 Boss 每帧各提交一次时，两个完整原生帧就可能占满四槽；保留一个空槽只能保护最后一次上层提交，无法解决全部槽已忙。C++ 的 `2 * BufferCount` 同样按提交量而非只按帧数安排容量。本轮在主槽满时只提交成图合成，不复制顶点／索引，也不重用主 allocator。实际双层的人工停 GPU 测试连续排入 24 次呈现，主槽与独立环用完后有 6 帧不满足覆盖，排空后下一帧恢复；正常六帧在途测试每帧单独检查，未出现该缺口。

持续暂停 GPU、并在停止消费的队列上继续无限产生呈现请求时，任何固定环最终都会用完。本轮显式验证 16 次合成仍连续，第 17 次达到硬界后丢弃；这与正常短时竞争及六帧在途测试分别报告，不把常见的更新锁竞争解释成允许闪烁。设备丢失、首次尚无有效成图或不兼容 viewport 变化时，也不能承诺用旧图补画。

低成本原因计数记录 GPU 锁、gate、绘制包锁、插件暂忙／重复、成图重放和隐藏决定。仅现有更新线程的有间隔诊断格式化和写日志，渲染线程不逐帧格式化或 IO。正式 DLL 不导出测试控制入口。

## 逐帧验证方法

探针加载实际核心、Boss 和 Minimap，共用生产 renderer；受控部分是游戏数据、输入和原生 UI 合成宿主。每一呈现先清目标，再执行生产 L／UI／H 路径，并为该次呈现建立独立 GPU 回读 ticket。回读和等待只在测试宿主执行，产品不读回或等待 GPU。重叠区域由实际 Minimap 的红色下层边框与 Boss 的深色背景确定，每一故障帧都检查覆盖，不能靠旧目标像素通过。

旧 `411bc63` 的实际 DLL 在新探针下稳定失败：重复序号的故障帧丢失 26,460／26,940 个重叠像素；输入新字符引起图集变化的故障帧丢失全部 26,940 个像素。对固定旧源码只添加快照锁故障钩子的 DLL，同样在锁竞争当帧丢失全部覆盖。另用已修状态但仍链接旧共享 UI 的中间 DLL，图集创建拒绝时上层网格数仍从 1,127 增至 1,134，直接暴露新 UV／旧 handle 混配，不能只凭背景像素把该分支算作通过。旧包、旧 DLL 和各次未通过记录单独保存，故障钩子版本另行标明，不冒充原游戏 DLL。新正例、命令、逐帧记录和资源边界结果见 [本轮证据目录](evidence/boss-continuity-2026-11-02/README.md)。

## 升级与最小复测

退出游戏后更新 `EROverlay.dll`、`overlays/Boss.dll` 和 `overlays/Minimap.dll`。本轮 Minimap 同样静态链接了共享字体图集创建暂忙的修复，因此三个 DLL 使用同一包。已有配置、`configs/boss-ui.json`、`configs/boss-revival.json`、`configs/boss-encounters.json` 和 `Challenge.txt` 保留；本轮没有配置迁移。

沿用现有加载方式进入存档，按默认 `=` 打开完整 Boss 面板，使其与 Minimap 重叠，观察稳定显示、滚动及输入新字符；关闭面板、打开全屏地图再返回，确认没有残影且输入恢复。加载速度仍需单独现场确认。本轮离线结果不替代这次复测，闪烁尚未现场验收。
