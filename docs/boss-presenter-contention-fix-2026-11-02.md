# Boss 成图锁竞争补充修复

代码提交：`9d623d0f4cc9063524b2538938f7505afdd1569f`。本轮补齐 `5ee822c` 父侧复验发现的缺口：已有有效成图时，另一 CPU 执行上下文持有成图锁，仍可让当前呈现漏掉 Boss。`5ee822c` 未向用户交付，不视为现场验收版本；最新现场反馈仍是 `411bc63` 闪烁。新包尚待游戏复测，菜单预加载也尚未得到现场确认。

## 锁忙不代表当前目标已经画好

原生 `scene.cpp` 的共享 SRW gate 保护回调生命周期，不串行不同 submit。每个调用借用自己的 sequence、RTV 和资源。调用 A 可在 `record_copy` 后持有 Presentation 锁、尚未 Execute；调用 B 进入另一个当前目标，经 render／painting 锁暂忙转入重放，再因同一 Presentation 锁暂忙直接返回。随后 A 提交的是 A 的 target，不能证明 B 的目标已有遮挡。

外层 `Runtime.presentation` 原来也用独占 Mutex，且同 device／queue 的普通准备过程每帧重新写入同一 handle。该临界区只有 Arc 元数据，没有当前 target 的绘制收据。两个锁都不能把「暂忙」解释为「已提交」。完整持有者、线程、固定源码行和时序见 [锁审查](evidence/boss-presenter-2026-11-02/lock-audit.md)。正常 update 和纹理准备线程不持 Presentation，新增测试线程不冒充已有生产维护线程。

固定 C++ 对照 `afab7e14db2b62ae0bede980d5d0c96634321350` 的 `overlayScene` 在入口用 `deviceMutex_` 串行绘制。Rust 为保持非阻塞，采用 try-lock 和成图重放；让重放再次依赖正在更新成图的独占锁，没有保住该串行结果。这里证明了生产允许的漏提交路径，没有现场线程记录证明它是本次游戏闪烁的唯一原因。

## 当前提交保证

`PresentationHandle` 改为 `Arc<Presentation>`。维护 Mutex 只管理成图分配、复制记录、发布和退休；重放从安全发布的不可变 Arc 读取成图，不取得该锁。16 个合成 allocator/list 各有自己的短期独占租约和 fence；当前调用选择可用槽，使用当前借用 RTV 提交，不保留游戏目标，不重放另一次调用的 command list。各槽独立计数和 Signal，避免并发共享 fence 值反序。

外层 handle 改为 RwLock，普通回调仅共享读取；同 identity 不再写入。只有尚无有效新成图的 renderer 初始化，以及停止排空后，才写该槽。新 renderer 成功发布 handle 后才安装到状态中。已有有效同 generation 成图的普通回调之间不再争用独占 handle 锁。

每次新图复制写入另一张闲置图片，不能改写正在发布或被回放租借的图片。否则另一 CPU 可能读到新像素配旧位置、裁剪或透明度。常态 current＋一张 idle 轮换；只在主复制 fence 已完成、没有 CPU／合成槽 Arc 租约时复用，连 Surface 的 Arc 分配也复用。64 组、128 SRV、128 MiB 上限不变；压力下只回收已完成且无租约的闲置图，不动当前图或在途资源。

关闭／隐藏立即增加对应 epoch，提交前再次核对全部成图 epoch。停止先永久关闭提交准入，再取得维护锁及全部录制槽检查 fence，覆盖已录制但尚未 Signal 的调用。最后复核之前已经收到的 hide／close 会取消该整包；没有声称复核之后任意纳秒的请求能撤销已提交 GPU 命令。viewport／device／queue、代次失效、非阻塞、原生 PIN 和输入释放规则保留。

安全发布使用精确锁定的 [arc-swap 1.9.3](https://docs.rs/arc-swap/1.9.3/arc_swap/)，避免自写裸 Arc 指针回收。只新增该运行时依赖及其编译期 `rustversion 1.0.23`，没有新增 DLL 或字体；两份 MIT 许可证随包保留。

## 故障当帧的反例与回归

固定 `5ee822c` 导出共 307 个文件，仅在 `layer_fixture.rs` 回移植持锁控制，其余文件逐字节一致。测试线程取得真实生产成图锁后确认握锁；直到当前原生 H 回调完成才释放并 join。每次呈现先清目标，分别建立 GPU 回读 ticket，不等松锁后才看恢复，也不用目标前帧像素。

| 另一 CPU 全程持锁时的当前帧 | 旧 `5ee822c` 故障帧 | 新实现对应故障帧 |
|---|---|---|
| 真实新图集 pending，必须沿用旧成图 | 26,940／26,940 个覆盖像素缺失 | 0 个缺失 |
| 重复 sequence，不能再次推进 UI | 26,460／26,940 个覆盖像素缺失 | 0 个缺失，input poll 不重复 |
| 核心 render Mutex 同时暂忙 | 26,940／26,940 个覆盖像素缺失 | 0 个缺失 |

最终正常 Boss／Minimap 与生产渲染路径的矩阵有 120 个稳态帧及 362 个独立矩阵回读；另用测试 Boss 加真实快照／UI 锁故障，为 120＋376 帧。普通应显示 Boss 的矩阵帧分别为 283、297，全部通过；判定允许坏像素不超过 ROI 的 1%，两轮各有 80 个 Boss 帧为 120／26,940，其余为 0，新增三类持锁故障帧均为 0。每轮还独立检查 44 个隐藏、5 个下层可见和 6 个开关过渡帧。真实关闭、全屏地图、loading、已隐藏后状态未知，在发布锁和 render 锁竞争下仍保持隐藏。

Renderer 还用另一 CPU 在「已录制、已 Close、未 Execute」处暂停，先返回 invalidate／close，再放行，确认当前清空目标仍无旧图；录制租约使 `wait_idle(0)` 返回未空闲，取消后槽可复用。未发布的蓝色 copy 不改变正在回放的绿色成图，确认发布后才变蓝；copy 持锁期间先失效再确认也不能复活。32 次正常更新仅创建两张资源和两个 Surface Arc，隐藏后释放；填满 128 个 SRV 后变尺寸仍能安全回收闲置图。

两套矩阵使用独立 fixture 核心，以控制游戏数据和原生合成宿主；实际插件、UI、网格所有权、原生 L／U／H 适配器和 GPU 提交使用生产代码。正常核心另有实际三 DLL 三轮检查，以及加入合法上层 fixture 的三轮在途退休检查。根目录 fmt、check、严格 all-targets Clippy、默认测试及 Release 全过：186 通过、0 失败、11 项外部检查默认忽略。独立干净浅克隆、全新 target、默认 feature、无游戏／C++ 资产再次全部通过，190 项独立代码包 manifest 匹配。该 190 项不代表最终文档包，也不替代最终安装 DLL 的哈希。

## 代价与有限边界

与 `5ee822c` 相比，16 个 allocator/list 槽不变，presentation fence 从 1 个改为 16 个；预留 Arc 租约容量为 16 × 64 × 8＝8,192 字节，另有容器和驱动自身分配。1080p 的正常成图由一张增加到两张 RGBA8 committed resource，多 8,388,608 字节；在途或退休时可能更多，仍受总 128 MiB 上限约束。每次新成图的复制载荷仍为 8,294,400 字节；单纯重放不重新复制图集或图片。

同一 renderer-only 场景和基准源码、Release 构建、RTX 4080、1080p、64 个四边形、三轮交替各 300 样本中，CPU p50 的三轮中位数为旧 23.1 µs、新 23.9 µs；GPU p50 均为 34.816 µs。每轮均为 0 次 Rust 分配、0 丢弃、2 次 draw，committed resource 峰值由 44,957,696 增至 53,346,304 字节。原始 p95／p99 和所有轮次保留，不凭这些小差异声称整体变快或完成游戏 FPS 验收。测量在计时外排空队列，不含 egui、核心插件分发、游戏及池初始化；驱动 fence／allocator 内存未计入资源字节。

人工完全暂停 GPU 并连续排入 24 次呈现时，每轮仍有 6 帧因固定池耗尽失去覆盖，排空后下一帧恢复。这与本轮修正的普通 CPU 维护锁竞争分别统计，未将后者改称过载。首次无图、不兼容设备或 viewport、所有 16 个合成槽同时在录制或 GPU 在途时，仍不能无限保证连续呈现。没有逐帧 GPU 等待、无限扩容、DXGI／Present hook 或独立窗口。
