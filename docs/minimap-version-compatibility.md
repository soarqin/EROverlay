# Minimap 历史版本兼容性分析

2026-10-02。分析范围为 `D:/Games/EldenRingExe/` 的全部 28 个版本目录，覆盖 1.02～1.17。目录中有 27 个独立 EXE；1.13 与 1.13.2 的 SHA-256、长度和内容完全相同。最新基准为 Steam 原始 1.17.1 EXE，PE FileVersion 为 `2.7.1.0`，SHA-256 为 `1a3547101327f65d0c76da2f9190ac0aa66871ea42bae2aecc61e11a8b597891`。

## 结论与覆盖边界

**当前工作区已接入全部 27 个独立旧 EXE 和最新 1.17.1 的适配信息。** [GameFiles](../src/gamefiles.cpp) 按完整 SHA-256 选择函数、全局地址和布局，再检查四个调用入口。28 个旧目录逐文件核对通过；1.13 与 1.13.2 共用一份适配信息。未知哈希仍禁用游戏调用。改动尚未提交或部署。

原生素材、地图碎片同步、死亡标记、编号标记和全开底图均已接入三类历史布局。文件 ABI 与原 allocator/请求退休逻辑保留；早期赐福使用 `0x2D0/+0x2C8`，后续使用 `0x350/+0x348`。PARAM 按目录格式和行边界读取，早期不访问后续 alternate 字段。

**支持超过三个图集的 mod。** 图集名称和数量来自内部 TextureAtlas 与 GFX 引用，容器不固定为三张或四张。12 个图集的一次文件提取、117 个可见图标的正式 ImGui 纹理/UV、失败隔离和回收验证已通过。旧版不请求的 DLC 图标按用户确认不作为兼容阻塞；缺少单个图标素材不影响其他有效图集。

提供的旧目录没有 GFX、TPF、地图索引或参数资源；本次用真实最新版资源和合成历史布局验证代码，没有启动各旧游戏。逐旧资源包的内容与画面仍待实测，不将离线通过写成全版本游戏测试通过。最新版此前的游戏测试结论沿用用户确认；本次新构建尚未部署。执行状态见[开发计划](minimap-version-compatibility-plan.md)。

## 分析方法与证据

针对后续游戏更新，已补充[通用扫描方案与接入计划](minimap-scanner-design.md)及 Python idapro 离线原型。共享规则从指令提取地址和布局，解析不查逐 EXE 哈希表，29 个目录／28 个独立 EXE 已通过。运行时接入尚未执行；本报告保留当前哈希适配实现的状态，长期方案以通用扫描文档为准。

EXE 逆向全部使用 Python `idapro 0.0.10` 和 IDA 9.4；没有附加调试器或设置断点。每份数据库打开后检查输入 SHA-256。用户目录中的现有数据库保持原样；分析缓存和完整函数导出存入 `build/ida/versions/`。

逐版定位过程使用 RTTI、字符串引用、PE 异常展开记录及其 chained unwind 信息。函数匹配使用 IDA 解码后的多段指令窗口，再检查完整指令边界、非重定位字节、内部分支目标，以及文件生命周期的跨函数调用关系。已有数据库元数据偶发返回空值时，拒绝使用该次结果并重新打开；最终证据均通过哈希核对。

- [机器可读证据](minimap-version-compatibility.evidence.json)：全部 SHA-256、函数 VA/RVA、全局地址、字段布局、参数组和精选指令。
- [跨版本 IDA 工具](../tools/ida_minimap_versions.py)：定位、导出和历史指令变体。
- [证据收集与复核工具](../tools/collect_minimap_version_evidence.py)：只读取 IDA 导出，检查全版本覆盖、哈希、指令、分支、调用和字段。
- [适配表](../src/util/gameprofiles.inc)与[生成/核对工具](../tools/generate_minimap_profiles.py)：从证据生成 28 个哈希条目，对全部旧目录和最新基准核对 PE 地址、入口字节和完整哈希。

所有地址的 ImageBase 为 `0x140000000`。版本目录名与 PE 版本并非同一种编号：例如目录 1.10 的 PE 版本为 `2.0.0.0`；1.13.2 目录实际包含 PE `2.3.0.0`。运行时应以完整哈希选择适配信息。

## 原生文件与 Overlay 自有纹理

全部旧 EXE 的下列函数与最新基准保持相同指令逻辑，变化是重定位地址：独立请求分配、64 字节请求提交、pending 列表、flush、任务 enqueue、取消、请求初始化、DCX、完成回调、cleanup 和请求退休。

- `ReadRequest` 的 allocator、alignment、callback、context、flags、parameter 和 priority 字段保持一致。
- manager 的 ending 字节为 `+0xE38`，flush 列表为 `+0xD70`，任务对象为 `+0x20`。
- callback 的前四个参数为 status、context、buffer、size；成功状态 `1` 转交 CPU buffer。原 allocator 的释放槽为 vtable `+0x68`。
- 请求完成后 cleanup 调用 pool retire；generation 在 `pool+0x50`，索引和 generation 仍为两段 U16。回调返回后再释放上下文的规则可以保留。

示例 RVA：

| 样本 | submit | flush | enqueue | cancel | manager 全局 | allocator 全局 |
|---|---|---|---|---|---|---|
| 1.02 | `0x263E250` | `0x263E430` | `0x26439D0` | `0x263D9B0` | `0x4524A40` | `0x3C70CE0` |
| 1.10 | `0x26A6E10` | `0x26A6FF0` | `0x26AC590` | `0x26A6570` | `0x45B41C0` | `0x3CFDF40` |
| 1.12 | `0x26EB9D0` | `0x26EBBB0` | `0x26F1150` | `0x26EB130` | `0x485CFE0` | `0x3D872E0` |
| 1.17 | `0x26EEAF0` | `0x26EECD0` | `0x26F4270` | `0x26EE250` | `0x48611A0` | `0x3D8B360` |

运行时仍应使用逐哈希证据表中的完整地址集合，不能从一个 submit 地址推算其他地址。各版本的文件桥可以继续把 CPU 字节复制到 Overlay 内存，再创建 Overlay 自有 DDS 纹理、SRV、上传队列和 fence。新 DDS/GPU 生命周期代码、离屏目标修复与 Win32 快捷键没有旧 EXE 专属 RVA 依赖；它们仍需要适配后进行组合验收。

## 死亡标记与编号标记

全部样本确认了同一组 view 字段：raw map `+0x14`、地图类别 `+0x24`、坐标 `+0x28/+0x2C`、地下 U8 `+0x30`、角度 `+0x34`、死亡 valid U8 `+0xA9`、死亡坐标 `+0xAC/+0xB0`、死亡地图类别 `+0xB4`。**地下状态必须继续只读一个字节**，此前修复对旧版同样适用。死亡读取源保持 GameDataMan `+0x40/+0x48`，Home 参数访问保持 row 0 的 `+0x278`。

编号列表位于 `view+0x300`，保存对象位于 `view+0x338`。保存对象的 slots、capacity 和 activeCount 分别为 `+8/+16/+0x40`。所有样本都保留十个 16 字节保存槽；正常放置上限的全局值逐版读取均为 `5`。槽位字段保持 `id@0`、`x/y@4/8`、`map U8@12`、`icon U8@13`。原生 UI 继续使用 icon 和 `slot+1` 数字，没有因删除前一个槽而重编号。

`death_marker=1` 和 `player_markers=1` 的读取与绘制路径已保留；menu→owner→view 由哈希布局选择。全部条目的正式读取验证覆盖死亡有效/清除、非连续编号、菜单和上下文失效；各旧版 GFX 实际节点仍属于对应资源包的运行验收。

WorldMapPieceParam 的组号 `88`、事件字段 `+4`、每地图 32 个 ID 的算法及 reveal 返回 `UINT32_MAX` 保持一致。事件仓库布局和 type 1/type 2 读取保持一致。参数仓库的组总数在 1.07 从 185 增至 186，在 1.12 增至 194，但本次使用的组号没有移动：

| 参数 | 组号 | 逐版结论 |
|---|---:|---|
| BonfireWarpParam | 43 | 每份 EXE 的 accessor 已确认 |
| WorldMapPointParam | 87 | 每份 EXE 的 accessor 已确认 |
| WorldMapPieceParam | 88 | 与最新基准相同访问逻辑 |
| GameSystemCommonParam | 141 | 与最新基准相同访问逻辑 |

仓库 stride 为 72，entry 位于 `repository+0x88+group*72`，cap/table 两次解引用均为 `+0x80`。正式 [ParamRows](../src/util/paramreader.hpp) 支持 accessor 中的 12/24 字节目录格式，检查大小端标记、数据/name 偏移和行边界。最后一行使用字符串区或原生 `table-16` 文件长度限定；无法确认边界时跳过该行。1.02 仅读取基础字段并禁用后期 alternate，避免整行套用 256/236 字节结构。后期 alternate 也要求该行确实包含相应字段。保护页验证覆盖早期短行和六种目录格式。

坐标转换器 array `+0xF8`、stride 48、count `+0x280`，以及 legacy 树查询和坐标转换格式可以保留。1.12 以前构造器只初始化 m60；1.12 起增加 m61。旧版应仅展示自身存在的地表/地下类别。

`full_map=1` 本身仅在 Renderer 中覆盖选图 mask，不写游戏或存档，不新增 EXE ABI。它可以复用旧版允许变体掩码和目录检查，但仍依赖正确的地图快照及旧资源目录。1.02 的 tile-span helper 有指令差异和受保护的跳转目标，当前默认 L0 的 41×41 网格与构造代码相符；不能据此将 L1/L2 的旧版跨度标为已验收。

## 图集、别名和资源格式

全部样本都保留 `01_Common` 和 `71_MapTile` 原生组及其相同路径选择标志。游戏 GFX 路径仍先检查 `menu:/Win/%s.gfx`，再使用 `menu:/%s.gfx`；图集路径、地图挂载、GFX tag 1009、矩阵、sprite 解析，以及 TextureAtlas 的路径/扩展名去除和区域查找逻辑一致。TPF 的 PC header、DDS offset/size、名称和 metadata 解析也逐版确认一致。

此前两个资源兼容障碍已处理：

1. `Resources` 只加载实际 GFX recipe 引用的图集，以内部 `01_Common` TPF 的 DDS 名称定位，使用动态容器和逐图集 CPU/GPU 状态。文件回调一次解析 TPF，各 part 分别发布结果。缺失/错误 DDS 不阻塞其他图集；必要的 Player/Dead/Home/Marker 素材读取失败时显示重试状态，日志记录名称。
2. M10 只在已确认有 m61 转换器的版本启用；DLC 前只要求 M00/M01。验证已覆盖移除 M10 与 DLC 图集后的资源加载和地表/地下全开变体。

别名始终来自内部 GFX 和 TextureAtlas。补充 Python idapro 导出确认 `0x140D643A0` 遇到同名 key 时销毁待插入节点并保留已有节点；实现保留归档中首次出现的别名。12 图集合成验证含一个未使用图集和一个重复别名图集，二者没有 DDS，也不会被请求。所有已发布 recipe 和容器结构保持不变；CPU 字节按图集 release/acquire 发布给 render，设备重建复用自有 DDS。

图集数量不再由名称列表限制，仍遵循已有格式和资源预算：单个 TPF 最多 4096 项、单包最多 256 MiB、单 DDS 最多 32 MiB、待上传字节最多 64 MiB、每帧上传预算 8 MiB、核心自有纹理最多 768 个，SRV 堆 1024 项。超过预算的纹理等后续帧再创建，不通过复用游戏 GPU 句柄绕开预算。

下列条件无法仅由本次 EXE 目录确认，均已保留为资源验收项：

| 条件 | 已知证据 | 后续确认方法 |
|---|---|---|
| 旧资源实际引用的图集是否完整 | 动态清单、12 图集与缺失项验证通过；没有旧 TPF | 正常启动对应旧游戏，检查实际 DDS/GFX 引用 |
| 旧版 GFX 版本和 UI 路径 | 引擎解析函数相同；没有旧 GFX | 检查 GFX header、Player/Dead/Home/MarkerList/Text_0 |
| 各地图掩码与全开瓦片是否完整 | EXE mask 算法相同；没有旧索引 | 核对每个 exists 瓦片的全开变体，区分实际地图类别 |
| PARAM 目录格式位及行长度 | accessor 支持相同格式；没有旧参数文件 | 检查格式位、row span，以及所读字段的边界 |
| 1.02 的 L1/L2 地图跨度 | helper 存在版本差异；运行时默认 L0 | 逆向受保护调用的静态路径，并结合旧资源核对 |
| 全部旧版实际游戏表现 | 未启动旧游戏 | 适配后验证放置/删除、死亡/回收、碎片变化、旋转和卸载 |
