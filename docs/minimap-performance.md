# Minimap 性能优化说明

2026-10-03，本次优化针对原生素材接入后的诊断开销、绘制线程工作量和显存占用。显示配置、死亡标记、编号标记、全开底图和动态图集保持原有含义。代码通过本地生产实现验证；本次改动尚未在游戏画面中实测。

## 日志关闭后的路径

`[diagnostics] log_file` 留空或文件未打开时，原生 API 的日志回调为 `nullptr`。PARAM 和图集错误路径在格式化、名称转换前判断回调；核心日志在获取 mutex 前检查文件。请求结果的字节汇总、日志刷新计时和文件写入也只在日志开启时运行。

移除每五秒的地图进度缓存比对、玩家/死亡/编号位置输出，以及纹理就绪和帧心跳日志。正常显示仍保留必要的地图进度读取与上下文一致性检查；关闭日志不会改变读取结果。

启用日志时保留资源请求、完成结果和资源错误。采用缓冲写入，由文件工作线程通常每秒刷新，进入空闲或退出时再刷新。绘制线程不写资源日志。异常退出可能丢失尚未刷新的末尾内容。

## 绘制与更新

| 原路径 | 当前路径 |
|---|---|
| 每次查询瓦片都格式化文件名并查字符串目录 | 加载目录时生成数值键和路径；已缓存瓦片直接按数值键查询 |
| 绘制线程请求文件、查询文件、解析 TPF/DDS 并复制数据 | 绘制线程提出请求；更新线程处理文件和 CPU 数据，并发布纹理 token |
| 每个缺失瓦片遍历整个缓存统计待处理请求 | 原子计数限制最多八个瓦片任务；只检查待完成任务 |
| 瓦片获取和绘制各查询一次纹理状态 | 瓦片获取时查询一次，绘制复用同帧视图 |
| 同一图集被多个图标重复查询 GPU 状态 | 每图集每帧至多查询一次；图标区域在定义加载时解析 |
| 更新与绘制复制整批赐福/地标 | 共享不可变装饰列表；编号 1～5 使用固定数组 |
| 更新回调占有全局插件锁，绘制等待资源解析 | Minimap 显式允许并发更新/绘制；旧插件仍保持串行回调 |
| 每帧遍历全部驻留纹理检查上传/回收 | 仅处理待上传或待回收纹理，空闲上传路径直接返回 |
| 圆形旋转时加载扩大后的矩形范围及额外瓦片圈 | 按圆形可见范围筛选，保留一个像素的采样边缘 |

GPU 对象和 fence 始终由绘制线程管理。CPU 排队接口只解析和复制 DDS，短锁发布请求。Minimap 的取消结果通过原子状态发布；停止和设备重建仍排除更新/绘制并发。

普通关闭或隐藏地图约十秒后回收未使用资源。打开游戏菜单时不再扫描赐福和地标；后台文件工作线程没有请求时等待通知，避免持续空轮询。

## 显存和上传限制

圆形、圆角、旋转和半透明地图的离屏纹理改为小地图尺寸。仍为每个后缓冲保留独立目标，防止不同帧采样同一目标。旧的整屏离屏接口保持可用。

本机 D3D12 `GetResourceAllocationInfo` 的三后缓冲示例：

| 显示条件 | 原整屏目标 | 当前局部目标 |
|---|---:|---:|
| 3840×2160 屏幕、648×648 圆形小地图 | 100,270,080 字节（95.625 MiB） | 5,505,024 字节（5.25 MiB） |

这项比较只包含三张离屏纹理，约减少 94.5%；不包含图集、瓦片、上传暂存或游戏自身显存。实际分配随设备与显示尺寸变化。

- 图集按可见图标需求上传，不在启动时上传所有可用图集。约十秒未用的图集会回收；CPU DDS 保留用于重建。
- 瓦片缓存采用最近使用顺序，最多保留 512 个记录，GPU 缓存目标为 64 MiB。新核心使用实际分配大小，旧核心按压缩 mip 数据和 64 KiB 粒度估计。
- 当前帧已使用的瓦片不会因超预算而删除。极小 `zoom` 的可见集合可能超过 64 MiB；回收等待 GPU fence，临时峰值也可能高于缓存目标。
- CPU DDS 排队总量保持 64 MiB 上限，单张 DDS 上限 32 MiB，纹理 token 数上限 768。
- 更新线程每次最多准备四张纹理、约 4 MiB 数据；绘制线程每帧最多提交四次上传、约 4 MiB 数据。超过字节预算的单张图集独占一次批次，避免永久饥饿。
- 在途上传暂存目标为 16 MiB、最多八张。单张大纹理允许在上传队列空闲时独占；该目标不包含 GPU 驻留纹理。
- 地图层或无关碎片变化不会清空整个瓦片缓存；按图层、级别、坐标和进度变体选图。游戏上下文世代改变、设备重建与退出仍清理旧任务和纹理。

## 验证与实际范围

现有离线工具调用生产 `Resources`、`Data`、`Renderer` 和 D3D12 上传实现。新增检查直接测量调用次数和资源生命周期，未编写一份独立算法来替代生产代码。

- `minimap_performance_verify`：已加载瓦片连续 1,000 帧不请求、查询或创建文件/纹理，每帧仅查询一次 GPU 视图；验证更新线程加载、世代取消、缓存复用、64 MiB 回收、当前帧保护和闲置回收。
- 同一工具持有日志 mutex，另一线程执行 100,000 次关闭日志调用，验证不会等待该锁；启用日志的缓冲、刷新和关闭内容一致。
- `minimap_atlas_verify`：启动不分配图集 GPU 纹理；只使用一个图集时仅分配一张，500 次引用每帧至多查询一次。保留 12 图集、117 个可见图标、缺失/损坏图集、失败恢复和重置/退出验证。
- `minimap_texture_verify`：真实 GPU 回读与 DDS 压缩块一致；并发准备 128 个请求；局部与整屏离屏目标的透明度、非零视口原点、尺寸切换、两个独立目标及回收均按像素验证。
- 死亡、编号 1～5、全开选图、地图进度、历史布局和命名预设继续使用原有生产实现回归。
- `plugin_thread_verify`：直接调用生产插件分发器，验证旧插件串行、显式允许的更新/绘制并发，以及销毁前等待活动回调结束。

当前代码的 Debug/Release 构建通过，核心、Minimap、Boss、Achievements 和 injector 均可构建。十一项离线检查全部通过；中英文 INI 的分区、键和值一致。配置验证同时更新了近期调整后的默认值断言，没有修改显示默认值。

调用次数和局部目标分配可以验证本次减少了重复工作，离线循环耗时不能当作游戏 FPS 提升。游戏内还需正常加载新核心与 Minimap，观察首轮资源出现、移动/传送、地表/地下/DLC 切换、死亡/编号标记、透明旋转模式、隐藏后恢复与分辨率变化；帧时间收益需要同场景实测。

## 接口兼容

保留旧 `EROverlayAPI` 布局。版本 1 的原生扩展在尾部追加 `queueDdsTexture`、`beginOffscreenRegion` 和 `textureMemoryBytes`，调用前分别检查成员所在长度与函数指针。`readGameLayout` 也按自身字段长度判断，避免扩展后把旧核心误判为缺少历史布局。

配合旧核心时保留有限的绘制线程上传和整屏离屏回退；本次 CPU 并发与局部目标收益需要同时更新核心和 Minimap。资源读取、原生图标数量和历史布局规则不因此改变。
