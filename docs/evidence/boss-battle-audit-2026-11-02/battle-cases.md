# Boss 战斗归并只读核对

2026-11-02。未修改生产源码或项目文档。研究输入为当前生产 EMEVD 读取器的冻结副本、原始 EMEVD 归档、实际英文 FMG，以及原 C++ `afab7e14db2b62ae0bede980d5d0c96634321350` 的 207 项名单。英文名单的 Git blob 与固定 C++ 来源相同，均为 `5fecd6cee99ab293ac37680d460605a7ad0e17c3`。

## 结论

在这组归档中，未发现旧名单里的连续多 Boss／多阶段战斗因为不同主完成旗标而被生产目录拆成多行。旧名单全部 207 个主旗标都有具名生命条证据；其中 27 个名称标记为 `&`、`x2` 或 `Duo` 的条目，每项的全部已启用具名生命条都归到同一个原有主完成旗标。不能据此证明任意 Mod 都遵守该模式。

Hinterland 两只大树守卫存在独立持久完成、独立奖励，以及部分共享收尾。按「独立可持久完成记录」保留两条有原始事件依据；按「共同激活的一次遭遇」定义战斗则存在另一种产品语义。共享条件和共享收尾本身不能区分这两种定义，不能仅据 `related_entities` 连通或名称相同就自动合并。

生产读取器冻结副本的 SHA256 为 `33C05F50BCDC5F07C3C7875F9A3FE7ABC0CF68093807434FF7FB4CBEE240732B`。它对目录内 588 份原始 EMEVD 展开，输出 349 条 enabled 具名生命条证据和 468 条 `2003[12]` 证据，得到 211 个非零已知主完成旗标。该统计包含 LOD 资源中的重复证据，不等于生产 PARAM 资源计划的脚本数量。

## Hinterland 的独立完成边界

地图为 `m61_50_47_00`，runtime variant 为 0。

- `2050472810#1..5` 只等待实体 `2050470800` 的 AI Battle 状态、BGM 状态和自身未完成旗标；`#9` 开启其 slot 0 生命条。`2050472811` 对实体 `2050480860` 独立执行同构逻辑，使用 slot 1。
- `2050472820#12` 只等待 `2050470800` 的 HP 归零，`#15` 等它死亡，`#16` 立即置 `2050470800`。另一只是否完成不是这些步骤的前提。`#32/#33` 随后发放独立 ItemLot `30935`。
- `2050472821` 对 `2050480860` 独立执行相同结算步骤，`#16` 写 `2050480860`，`#33` 发 ItemLot `30950`。
- 两个结算事件的 `#17..20` 会在另一只仍战斗时重新显示它的生命条；`#23..28` 同时读取两个旗标，选择普通 Banner 或完整 HandleBossDefeat 收尾。这是共享收尾的真实证据，但发生在自身持久完成写入之后。
- 原生 `GameAreaParam` 行 `2050470800` 和 `2050480860` 分别使用同名独立 `defeatBossFlagId`，地图字段分别为 `[61,50,47]` 和 `[61,50,48]`。这里引用的是字段关系，没有用位置判定战斗身份。
- 原 C++ 同样按这两个主旗标独立记录进度。两份复活配方共享场地辅助旗标 `2050470400/2050475000`，但各自只清除自己的主完成旗标，没有顺带清除另一只的主旗标。

因此，不能把这两个实体等同于 Altus 共用单一主旗标、结算前要求两者都死的双大树守卫。若将 Hinterland 定义为一条遭遇，则至少需要明确双方旗标 AND 才完成、单只完成时的部分状态，以及两套复活操作如何呈现；这些是新的语义选择，不能由同名或共享 guards 自动得出。

## Abyssal Woods、Dane 与节庆

- Midra：`m28_00_00_00` 的 `28002811#16` 先检查人形实体 `28000801` 的 HP；随后进行过场并切换到 `28000800`。只有 `28000800` 出现 enabled `2003[11]`，`#12/#38` 是同一命名生命条的两个分支，不是两名 Boss。共同主旗标是 `28000800`；`28003811` 是阶段状态。
- Jori：具名条是 `m61_52_43_00` 的 `2052432810#139`，实体 `2052430800`。结算 `2052432800` 同时读写 `2052430800` 与过渡／恢复状态 `2052432848`；显示事件只把前者作为持久 Boss 保护条件。召唤实体没有各自的具名生命条，不能据批量禁用角色指令增加战斗行。
- Dryleaf Dane：`m61_49_44_00` 的 `2049442802#42` 启用实体 `2049440710` 的具名条，name ID `142501`。`2049442800#2..4` 要求它死亡并满足挑战状态 `2049442810`，`#9` 才写 `2049440800`。人物自身实体 ID 与主完成旗标不同，不能按数字相似性或通用 NPC 身份归并。
- Redmane 节庆：duo 的两条生命条只共同写 `1051360800`；显示／结算事件还读取节庆状态 `9410/9413`，但它们不是这场战斗的主完成写入。Starscourge Radahn 在 `m60_52_38_00` 的 variant 2 构造路径中，实体 `1052380800` 的最终主旗标为 `1252380800`。节庆、任务状态和共享场地条件不能作为把它们串成同一战斗的边。

## 同旗标跨地图和 variant

这组原始资源中，已解析完成旗标跨资源地图出现的 10 组均为同一 `[area,block,sub]` 的 `_00` 与 `_10` LOD 资源：`1044360800`、`1044530800`、`1045390800`、`1045520800`、`2044450800`、`2044470800`、`2045440800`、`2046450800`、`2046460800`、`2047450800`。没有发现同主完成旗标跨不同 runtime variant 的实例。

这说明当前归档中的跨文件合并未造成已知误合并；不证明「主旗标相同」在任意 Mod 的不同场地／不同 ceremony 中必定意味着一场连续战斗。共享持久旗标本身首先证明共享进度状态。若新增更强的成员身份，应保留 canonical map 和 runtime variant 证据，并明确 LOD 资源别名。

## 有用的回归

1. 真实归档检查 chiefs 的两个同名成员、Altus 两个同 name ID 的实体、Crystalian 三成员、Gargoyles 两成员都只生成一条战斗，并保留各实体证据。名称字符串数量不得代替成员数。
2. Godskin Duo 公共血条加两个实体的实际桥接指令；Godfrey 同血条改名、Radagon 两实体和 Scadutree Avatar 三实体连续阶段，完成条件均保持最终主旗标。中间阶段旗标不生成独立战斗。
3. Hinterland 两个独立主旗标：共享 guards、共享相关实体、相同文本和共用收尾均不能单独触发合并。分别置其中一个旗标时，另一条仍为未完成；若产品改为遭遇合并，应改测明确的部分完成及最终 AND 状态。
4. 同 canonical map 的 `_00/_10` LOD 资源仍能合并同一证据；不同 map／variant 复用实体号的未知条件不可误合并。新增跨场景同 flag 合并规则时，需给出明确的语义回归，而非从原版缺少反例推导普适性。
5. Jori 的辅助过渡旗标、Dane 的挑战状态、Redmane 节庆状态，以及 Radagon 的阶段／结局状态，均不能成为另一场战斗的身份或完成条件。

本次为静态归档与生产读取逻辑核对，没有运行或注入游戏，也没有验证动态加载时机、所有 Mod、同场景 FPS 或实际复活行为。
